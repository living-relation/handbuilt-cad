# Agent guide (Claude, Cursor, Grok Bot and any other agent)

## Read first, before starting work or asking
Before starting work or asking the maintainer anything, read in order: (1) this repo's agent guide
(`AGENTS.md`), (2) its binding rules / decisions file if it has one (`CONTRIBUTING.md`, `drawing/DRAWING-RULES.md`), (3) the shared
live state in this repo: `STATE.md` on main, this branch's `STATE-<slug>.md` (committed on the branch) on a branch,
`BACKLOG.md` and `archives/`. No HANDOFF/handoffs files; STATE-<slug> is the handoff. Archive the state file as
the PR's last commit. (4) Notes only (preferences, machine facts, gotchas; no status) in the memory store:
Project memory: <Projects>\_claude\Claude Projects\Working Memory\memory\handbuilt-cad\INDEX.md
(WSL: that same folder under the Windows Projects root). If a rule or note already answers a question, act on it and cite it - never ask the
maintainer something the rules already answer. When you do ask (Dan): always multiple
choice, labelled with one letter plus a number (a1, a2), with a recommended answer when
there is one.

This file is the single agent guide for this repo. `.cursor/rules/cad.mdc` only points here.

**State and decisions:** the current goal lives only in `STATE.md` (schema v1; a branch's own state in `STATE-<slug>.md`), open items in `BACKLOG.md`, finished state in `archives/`; dated decisions in `DECISIONS.md`. Scripts and hooks are registered in `automation.yml`. The `commit-msg` hook warns when code changes without one of these being updated (skip one commit with `[no-state]`).

## Before you change anything
1. Read this file, `CONTRIBUTING.md`, and the hooks/CI that apply (`.githooks/`, `.pre-commit-config.yaml`, `.github/workflows/` if present). Follow them. If a planned step would bypass a hook or gate, stop and ask the maintainer.
2. Never use `--no-verify`, never force-push, never push to `main`. Work on a branch and open a PR. Exception: the skill-zips CI bot may force-push (with lease) its own `chore/skill-zips` branch only.
3. Skill zips (`skills/<name>.zip`) are rebuilt automatically by CI; don't edit by hand. Never commit or push other generated or bot-owned files by hand; let the workflow that owns them regenerate them.
4. One clone per machine. On Windows + WSL it is the Windows clone (`<projects>\active\handbuilt-cad`); WSL sees the same files through the link `~/projects/handbuilt-cad`, so there is no WSL clone to keep in sync. Run git from Windows; pull with `git pull --ff-only`, one repo at a time; no batch pull/push scripts. In WSL use the Linux venv (`$CAD_PY`, default `~/.venvs/handbuilt-cad/bin/python`), never the repo's Windows `.venv`.
5. Use the repo's own venv (`.venv`, built by `setup.sh` from `uv.lock`). Don't install into system Python or into another project's venv. No code here imports from FreeCAD's bundled Python.

## Files that never go in this repo
- Part/model files (STEP, STL, 3MF, F3D, FCStd, PLY, OBJ, IGES, BREP, GLB), solver outputs, archives, files over 1 MB. Finished models go to `$MODELS_DIR/<job>/rev<LETTER>/` as AP242 STEP (see `skills/publish-to-models`).
  Exception: Claude-importable skill zips at `skills/<skill-name>.zip`, rebuilt automatically by `.github/workflows/skill-zips.yml`. Do not add other archives.
- Plugin manifests may be committed: `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.cursor-plugin/plugin.json`, and `.cursor-plugin/marketplace.json`. They have no `version` field. The Claude catalog name is `handbuilt-cad-plugins` and its only entry is handbuilt-cad at source `./`. On claude.ai, Turn Sync automatically on for that catalog so updates arrive after merges to main. Check for updates in the catalog forces it sooner. Where that switch sits on the page is unverified until someone clicks through Customize. The Cursor marketplace lists only this plugin at source `.`. Running the install-plugins script copies `.cursor-plugin` and `skills` to `~/.cursor/plugins/local/handbuilt-cad` and replaces the old copy. A Cursor local copy still updates by re-running the install-plugins script. Skills stay in `skills/<name>/SKILL.md`. The plugin ships no hooks, no MCP server, and no `bin/`.
- Secrets, `.env` files, tokens, personal paths or personal data.

## CAD and drawing rules
The drawing engine's full rule list (and which ones it enforces) is `drawing/DRAWING-RULES.md`; rev letters come from `drawing/revs.py`. CNC machined parts also follow `docs/CNC-MACHINING-RULES.md`. 3D printed parts use the wall rule in item 7.

1. **Model drives the rev letter.** The model generates the drawing; model and drawing rev letters always match. Letters start at A, skip I, L, O and Q, then continue AA, AB, ... after Z. Rev A is only for new models; an existing model's letter comes from counting its past releases.
2. **Clerical vs model revs.** Drawing-only edits that don't affect fit, form or function add a decimal (C -> C.01, C.02 ...). A model change bumps the letter for model and drawing (C.0x -> D) and resets the decimal.
3. **Redline workflow.** Mark up the drawing first, update the model to match, then regenerate the drawing from the model. Never fix a design issue on the drawing alone.
4. **Rev log table** at the top-right of sheet 1: Rev, Description, By, Date (dd/mm/yy). One entry per PR/release, not per edit; clerical revs are not listed; Rev A is "Initial"; drop the oldest rows when it gets too long. Template: `drawing/templates/REVLOG.md`.
5. **No hidden lines.** Center marks and center lines are fine.
6. **Smooth bodies, no mesh** in renders or drawings.
7. **Walls.** CNC machined parts use the wall minimums in `docs/CNC-MACHINING-RULES.md` (0.030" / 0.762 mm metal, 0.060" / 1.52 mm plastic or composite, or a stricter project value). A thinner CNC wall fails. 3D printed parts: the minimum applies to critical or structural features only. Anything questionable (e.g. a thin non-structural printed wall) is flagged for the maintainer to change or approve, never auto-fixed or auto-failed, and never assumed. `tools/cnc_check.py` defaults to the CNC metal floor; use `--process printed` (and `--min-wall` / spec / `--walls-config`) for printed bodies, otherwise printed walls are "not checked".
8. **Edge breaks are never auto-applied** (`docs/CNC-MACHINING-RULES.md` CNC-EDGE-BREAK). If chamfers or fillets are already modeled, do not prompt and do not add a general note; dimension their actual size. If they are not modeled and exposed sharp edges could cut hands, prompt the user; only if they approve, add a leader `BREAK ALL EDGES, STD` or a chamfer length they gave. When modeling a break, prefer a 45° chamfer. Tools that add chamfers run only when the user explicitly asks.
9. **Dimension each feature once.** Use an (xN) count for repeats, e.g. "Ø6.6 (x4)".
10. **Correct view.** Put each dimension in the ASME/ISO-correct view; chain, baseline and ordinate styles are all fine.
11. **Fillets go last.** Any fillet that fails is listed in the build report and drawing notes, never dropped silently.
12. **Made with.** Each version's `SUMMARY.md` has a "Made with" line naming the tool (and version, else "unconfirmed"); the revision register has a "Made with" column (`drawing/templates/DRAWING-REVS.md`).
13. **STEP only in the models folder.** AP242 STEP and drawings only. No .f3d, STL, or other model format is filed there. A print mesh, if a job needs one, stays in the parts home.
14. Project-specific naming rules (e.g. whether file names carry rev letters) live in that project, not here.
15. **Capped sections only.** Every rendered section view uses closed-surface clipping: the cut part is a closed solid with its cut faces filled (caps). Never clip just the outer skin; open cut faces render as hollow shells and misread wall thickness. Use `tools/render/section.py` (or `smooth_render.py --section`); the drawing engine's section views are capped too. All of them refuse an open cut.
16. **Version folders.** A models job is `$MODELS_DIR/<job>/rev<LETTER>/` (clerical `rev<LETTER>.<NN>/`). Existing job folder names are kept as they are; a new job folder is the plain subject. `tools/rev.py` makes the next version folder and its `SUMMARY.md`, never edits an existing one, and never converts old numeric `revN` folders.
17. **Initials, never agent names.** DRAWN = the person on Rev A; rev-log BY = the person who requested the change (`drawing/DRAWING-RULES.md` rule 32). They come from `~/.drawing-initials` (or env `DRAWING_INITIALS`); if missing and you are an agent (no terminal) the tool stops - ask the maintainer for the requester's initials, never guess or use "Claude" / "SteveCAD".
18. **Revision triangles.** Every full-letter rev puts its letter in a triangle next to each changed item (and the BOM row of a changed part number); .01 clerical revs have none and are not in the rev log (`drawing/DRAWING-RULES.md` rule 33, `drawing/revmarks.py`). Old triangles stay on later revs by default.
19. **Retention: two versions per assembly.** Keep the 2 latest versions of each assembly (its version folders, with the parts inside them); older versions are deleted after the new one is filed and checked (`tools/rev.py <job> --prune --apply`; Daniel, 2026-11-20, supersedes 2026-11-04). Clerical decimals go with their letter. Never delete a 3D scan. Scripts, runs, scans and working notes stay in the parts home (`~/cad-parts/<job>/`, `tools/paths.py`), not in the models folder.
20. **One part, one solid.** A part is one solid. A part that installs in its own step (for example legs that cover screws) is its own part. Several pieces are an assembly or subassembly of linked parts, never one fused body.
21. **External STEP files.** Every part and subassembly is its own AP242 STEP and opens from the top assembly (Fusion: linked component, right-click > Open). The release is the assembly STEP at the version root with AP242 external references to `Parts\<part>.stp`; bought parts' maker STEPs go in `Parts\` too. SR fastener bodies may stay inside that STEP. `tools/step_release.py` writes this.
22. **Fasteners: always SR Fasteners, no exceptions** (Dan, 2026-11-23). Every screw, nut and washer in every model build is inserted with Dan's SR Fasteners Fusion add-in, never modeled by hand, imported from a maker STEP or drawn any other way. They stay as separate bodies inside the assembly or subassembly; that is the only exception to rule 21. If SR Fasteners does not offer the fastener a design needs, stop and ask Dan; do not model it another way. An assembly built outside Fusion (scripts with this toolkit) is built without fasteners; its fasteners are added with SR Fasteners only after the assembly is in Fusion (Dan, 2026-11-23). Fasteners are never modeled, downloaded or re-modeled locally for each build (no part bloat on disk). Press-in hardware (PEM self-clinching nuts, studs and standoffs) and spacers such as EFC also come from SR Fasteners (Dan, 2026-11-23). Every hole, edge distance, centerline-to-edge, sheet thickness and hardness for press-in hardware follows the maker's own spec documentation (PEM catalog and per-part drawings), always, cited on the drawing or in the build notes; a value with no maker source is TBD, never a guess.
23. **One AP242 STEP.** Export to AP242 STEP and file that file only. A Fusion model keeps its .f3d in Fusion's cloud, not in the models folder. Never file two STEP files of the same item in one version. A header that is not AP242 fails `tools/checks/release_structure.py`.
24. **One assembly.** One source-of-truth assembly, always built from the newest part models. No duplicate per-rev copies (Fusion: one parts folder, one assembly, updated as new versions).
25. **Release checks.** `tools/checks/release_structure.py` fails more than two model versions in a job, a non-AP242 STEP, a non-STEP model file, a duplicate STEP, a made part with more than one solid, a bought part with no maker STEP, an assembly that embeds parts or references a missing one, a part in `Parts/` that no assembly uses, or a script, run, scan, or working note in the models folder. Live Fusion checks stay a checklist in `skills/publish-to-models`.
26. **Assembly-only drawings.** Only assembly drawing packages (11x17, build order and installation) plus a one-page printed parts list for assemblies with 3D-printed parts; no separate part drawings or DXFs (`drawing/DRAWING-RULES.md` rules 40-41, `skills/cad-drawing`). Full models are still required for every part.
27. **Materials** (Dan, 2026-11-23). The material on the drawing and in the BOM is the one that counts; a Fusion material is only a file property, not a rule, and a model is a visual representation of the design. Assign each part its correct Fusion material when it is modeled, so the BOM needs no hand editing. Where Fusion has no match (most print filaments, e.g. PA12 MJF; Fusion's default is aluminum), keep the nearest Fusion material for the look and carry the real material in a user-editable material field (HB BOM `material`, a component attribute or a user parameter) that the BOM and drawing read, instead of the Fusion material. The user chooses whether that field is shown as the part's material property. The part description says whether a part is printed or machined.
28. **Where created: one build method per model, recorded, kept** (Dan, 2026-11-23; vitally important). Every CAD model is always rebuilt with the method that created it: the same tool and the same source (a script and the engine that runs it, for example build123d / CadQuery in the CAD venv, a Fusion API script run in the Fusion app, or a hand-modeled Fusion document). A model generated by scripts with this toolkit keeps being generated that way; a Fusion model stays a Fusion model. Every model has a "where created" record that persists in its project repo: a `MADE-WITH.md` beside its source (per file: tool, script path or Fusion document, evidence) and a line in the project's model list or state pointer, so a later session never has to guess. Read it before touching a model. A change of method is Dan's decision only, made after the new method's output is compared with the old one and shown to match; the record is then updated in the same PR. Fusion models exist so Dan can view and draw them: the deliverables are an AP242 STEP of the assembly (for the assembly drawing) and a STEP of every machined and 3D-printed part (to make it). The rule covers how the model itself is built, not the tools around it: any other tool may be used for work that supports it (FEA and other simulation, checks, measurement, comparisons, drawings, conversions), blending methods wherever one tool makes a job easier (Dan, 2026-11-23).
29. **Fusion models live in the work hub** (Dan, 2026-11-22). Every Fusion model is saved in the SparkleBots hub, project Dan, folder Personal/<project name>; the personal hub is retired (its trial ends). Every model being worked on is also exported as an AP242 STEP to the models folder (rules 13, 23).
30. **Model first, then everything from the model** (Dan). Change the model, then regenerate its drawings; parts lists and BOMs are generated from the model too, never typed or edited by hand (rule 3, drawing rule 6). A wrong BOM row is fixed in the model (part name, number, material property or SR Fasteners part) and regenerated.

## Fusion MCP
Fusion work uses Autodesk's official, Autodesk-hosted MCP servers (nothing to install): Fusion Compute MCP `https://developer.api.autodesk.com/da/v3/mcp/fusion` (preferred, headless cloud Fusion, so local Fusion isn't interrupted); Fusion Data MCP `https://developer.api.autodesk.com/fusion/mcp`; Fusion Desktop MCP is built into Fusion (Preferences > General > API, local `http://127.0.0.1:27182/mcp`). Docs: https://help.autodesk.com/view/ADSKMCP/ENU/. This rule moved here from the shared tools repo on 2026-11-22; it is the one copy.

## Electrical and design plans
1. **Plan document.** Every design with electronics includes a plan document with wiring tables, a schematic, and an electronics BOM.
2. **Wiring tables.** List every required wire for each device signal. If GPIO/PCB pins can't be planned yet, leave the pin as TBA instead of assigning one.
3. **Real wiring.** Electrical designs carry real planned wiring (wire gauges, connectors, routing) and real device specs.
4. **Off-the-shelf CAD.** Off-the-shelf parts (dev boards, extrusion brackets, plates and similar hardware) use the supplier's official CAD model. Fasteners are the exception: they come only from SR Fasteners (rule 22). Every other bought part is the maker's downloaded CAD model, and it must be accurate; where the maker publishes none, model the closest approximation from the maker's drawing, with the drawing number and every dimension source cited in the part's `MADE-WITH.md` (Dan, 2026-11-23). A bought part with no maker model fails `tools/checks/release_structure.py`. Put the supplier's part number on the BOM. Save every part model, purchased and fabricated, in a `parts/` folder inside the project.

## Folder notes
Every folder the toolkit creates or uses (the parts home `~/cad-parts` root, its `_archive`, each `<job>`, `<job>/src`, `<job>/runs`, the models folder and each models job folder) has a README.md or AGENTS.md saying what is in it, who owns it, and where its paired folder is. An agent that creates a new job or folder adds one from `templates/notes/` (`tools/folder_notes.py` writes a note only when it is missing, never overwriting; it is the only writer of these notes, called by `setup.sh` and publish-to-models). Parts-home job folders are named `<name>_<MMDD>`. A models job folder is any folder holding `rev*` version folders, whatever its name (rule 16). Other folders are reported as warnings. `tools/folder_notes.py --check` lists folders missing one. This is the full rule.

## Linux runtime
Open3D needs the system library `libEGL.so.1`. On Ubuntu install it with `sudo apt-get install -y --no-install-recommends libegl1` or `import open3d` fails. `setup.ps1` installs the sim apt packages in `apt-sim.txt` as root through `wsl.exe -u root` (no WSL password); `bash setup.sh` run directly tries `sudo -n`, then a sudo prompt only in a terminal, the sim venv and uv, then runs `scripts/verify-install.sh`, which fails with a list of anything missing. `--no-sim` / `-NoSim` skips the sim tools. Fairsolid stays optional (`--with-fairsolid`).
